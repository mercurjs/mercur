`PayoutModuleService` reads and writes payout records, and it’s the only code that calls the payout provider. Resolve it from the container in subscribers, jobs, steps, and routes. Prefer the [workflows](/platform/payout/reference/workflows) when you also need links, events, or a rollback.

## Resolve the service

The service is registered under `MercurModules.PAYOUT`, whose value is `"payout"`:

```ts
import { MercurModules } from "@mercurjs/types"

const payoutService = container.resolve(MercurModules.PAYOUT)

const [payouts, count] = await payoutService.listAndCountPayouts(
  { status: "on_hold" },
  { take: 20, order: { created_at: "DESC" } }
)
```

## Generated methods

The service extends `MedusaService({ Onboarding, Payout, PayoutAccount, PayoutReversal })`, so each model gets Medusa’s standard methods:

| Model | Methods |
| --- | --- |
| `PayoutAccount` | `retrievePayoutAccount`, `listPayoutAccounts`, `listAndCountPayoutAccounts`, `createPayoutAccounts`, `updatePayoutAccounts`, `deletePayoutAccounts`, `softDeletePayoutAccounts`, `restorePayoutAccounts` |
| `Onboarding` | `retrieveOnboarding`, `listOnboardings`, `listAndCountOnboardings`, `createOnboardings`, `updateOnboardings`, `deleteOnboardings`, `softDeleteOnboardings`, `restoreOnboardings` |
| `Payout` | `retrievePayout`, `listPayouts`, `listAndCountPayouts`, `createPayouts`, `updatePayouts`, `deletePayouts`, `softDeletePayouts`, `restorePayouts` |
| `PayoutReversal` | `retrievePayoutReversal`, `listPayoutReversals`, `listAndCountPayoutReversals`, `createPayoutReversals`, `updatePayoutReversals`, `deletePayoutReversals`, `softDeletePayoutReversals`, `restorePayoutReversals` |

The generated create and update methods write rows only. They never call the provider.

## Provider-backed methods

These methods call the payout provider as part of the write.

### createPayoutAccount

```ts
createPayoutAccount(input: CreatePayoutAccountDTO): Promise<PayoutAccountDTO>
```

Creates the row, calls the provider’s `createAccount` with `data.account_id` and `metadata.account_id` set to the new id, then stores `external_id`, the flags, the derived `status` and `kyc_status`, and the provider’s `data`. Deletes the row if the provider throws. `input` takes optional `data`, `context`, and `seller` (used when `onboarding.prefill` is on).

### updatePayoutAccount

```ts
updatePayoutAccount(accountId: string): Promise<PayoutAccountDTO>
```

Re-reads the account with the provider’s `retrieveAccount` and stores the same fields as `createPayoutAccount`, plus `last_synced_at`. Clears `onboarding_token` once details are submitted. The account `status` and `kyc_status` are derived here from the provider’s flags, requirements and `disabled_reason`.

### createOnboarding

```ts
createOnboarding(input: CreateOnboardingDTO): Promise<OnboardingDTO>
```

Publishes the link the seller follows next and stores it on the account’s onboarding record:

- Before the seller submits their details, it calls the provider’s `createOnboarding` with `refresh_url` and `return_url` from `input.data` or the module’s `onboarding` options, and stores the link with `kind: "onboarding"`. It creates the account’s `onboarding_token` for the refresh URL if it’s missing.
- Once `details_submitted` is set, it asks the provider’s `createLoginLink` for a dashboard link and stores it with `kind: "login"`. A provider without `createLoginLink` gets a new onboarding link instead.

`input` takes `account_id` and optional `data` and `context`.

### processPayout

```ts
processPayout(payoutId: string): Promise<PayoutDTO>
```

Sends a `pending` or `failed` payout with the provider’s `createPayout`, passing the order id as `group`, the payment in `data.source_payment`, and `{ payout_id, order_id }` as metadata. Like Medusa’s `capturePayment`, it locks the row and marks it `processing` in a transaction, then calls the provider outside it, so the lock is never held across the provider call. Stores the provider’s `status` and id. A provider error is recorded on the row as `failed`, or `aborted` when it’s a `PayoutProviderError` with `final: true`; it doesn’t throw. Any other status is returned unchanged.

### processPayoutReversal

```ts
processPayoutReversal(reversalId: string): Promise<PayoutReversalDTO>
```

Sends a `pending` or `failed` reversal with the provider’s `reversePayout`, against the provider id kept in the payout’s `data.provider.id`. Locks and records errors the same way as `processPayout`.

### getWebhookActionAndData

```ts
getWebhookActionAndData(
  input: PayoutWebhookActionInput
): Promise<PayoutWebhookResult>
```

Passes `{ data, rawData, headers }` to the provider and returns its action and the provider’s object id. It doesn’t change any record.

### getOptions

```ts
getOptions(): ResolvedPayoutModuleOptions
```

Returns the resolved module options, `onboarding.returnUrl`, `onboarding.refreshBaseUrl`, `onboarding.prefill`, and `onboarding.defaultCountry`, with defaults applied. Scheduling options belong to the integration that runs the payouts, such as the Stripe connector plugin.

## Idempotency keys

Each provider-backed method sets `context.idempotency_key` before it calls the provider:

| Method | Key |
| --- | --- |
| `createPayoutAccount` | The new `pacc` id, unless you pass one |
| `createOnboarding` | The `account_id`, unless you pass one |
| `processPayout` | The `pout` id, then `<id>:<attempt>` on retries |
| `processPayoutReversal` | The reversal id, then `<id>:<attempt>` on retries |

A provider caches a key with the request that first used it, so a retry after a refused attempt needs a fresh key. The attempt count is stored in the row’s `data.attempts`. Stripe Connect forwards the key to Stripe on account, transfer, and reversal creation.
