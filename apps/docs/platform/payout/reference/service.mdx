`PayoutModuleService` reads and writes payout records, and it’s the only code that calls the payout provider. Resolve it from the container in subscribers, jobs, steps, and routes. Prefer the [workflows](/platform/payout/reference/workflows) when you also need links or a rollback.

## Resolve the service

The service is registered under `MercurModules.PAYOUT`, whose value is `"payout"`:

```ts
import { MercurModules } from "@mercurjs/types"

const payoutService = container.resolve(MercurModules.PAYOUT)

const [payouts, count] = await payoutService.listAndCountPayouts(
  { status: "paid" },
  { take: 20, order: { created_at: "DESC" } }
)
```

## Generated methods

The service extends `MedusaService({ Onboarding, Payout, PayoutAccount })`, so each model gets Medusa’s standard methods:

| Model | Methods |
| --- | --- |
| `PayoutAccount` | `retrievePayoutAccount`, `listPayoutAccounts`, `listAndCountPayoutAccounts`, `createPayoutAccounts`, `updatePayoutAccounts`, `deletePayoutAccounts`, `softDeletePayoutAccounts`, `restorePayoutAccounts` |
| `Onboarding` | `retrieveOnboarding`, `listOnboardings`, `listAndCountOnboardings`, `createOnboardings`, `updateOnboardings`, `deleteOnboardings`, `softDeleteOnboardings`, `restoreOnboardings` |
| `Payout` | `retrievePayout`, `listPayouts`, `listAndCountPayouts`, `updatePayouts`, `deletePayouts`, `softDeletePayouts`, `restorePayouts` |

`createPayouts` isn’t in the `Payout` row because the service overrides it. The generated create and update methods write rows only. They never call the provider.

## Provider-backed methods

These methods call the payout provider as part of the write.

### createPayoutAccount

```ts
createPayoutAccount(input: CreatePayoutAccountDTO): Promise<PayoutAccountDTO>
```

Creates the row, calls the provider with `data.account_id` set to the new id, then stores the provider’s `data` and `status`. Deletes the row if the provider throws. `input` takes optional `data` and `context`.

### createOnboarding

```ts
createOnboarding(input: CreateOnboardingDTO): Promise<OnboardingDTO>
```

Calls the provider with the account’s `data` merged with `input.data`, then creates the onboarding record or updates the existing one. `input` takes `account_id` and optional `data` and `context`.

### createPayouts

```ts
createPayouts(input: CreatePayoutDTO): Promise<PayoutDTO>
```

Takes one payout, not an array. Throws a `NOT_ALLOWED` error when the account isn’t `active`. Otherwise it creates a `pending` row, calls the provider, and stores the provider’s `data` and `status`. Deletes the row if the provider throws. `input` takes `account_id`, `amount`, `currency_code`, and optional `data` and `context`.

### getWebhookActionAndData

```ts
getWebhookActionAndData(
  input: PayoutWebhookActionInput
): Promise<PayoutWebhookResult>
```

Passes `{ data, rawData, headers }` to the provider and returns its action and Mercur id. It doesn’t change any record.

### getOptions

```ts
getOptions(): PayoutModuleOptions
```

Returns the resolved module options (`onboarding`, `capture`, `transfers`, `reversals`, `settlements`, `notifications`, `alerting`, `kycMonitor`, `webhookDelay`, `webhookRetries`) with defaults applied. Every scheduled job reads them. See [The payout pipeline](/platform/payout/concepts/payout-pipeline).

## Idempotency keys

Each provider-backed method sets `context.idempotency_key` before it calls the provider, unless you pass one:

| Method | Default key |
| --- | --- |
| `createPayoutAccount` | The new `pacc` id |
| `createOnboarding` | The `account_id` |
| `createPayouts` | The new `pout` id |

`createPayoutWorkflow` passes the order id, which replaces the `pout` default. Stripe Connect forwards the key to Stripe on account and transfer creation.
