The payout pipeline is the path from a placed order to money in a seller’s account. Mercur ships the building blocks: the workflows, the webhook route and subscriber, and the provider interface. It doesn’t ship the scheduler that decides when an order is paid out. You choose that moment and call `createPayoutWorkflow` yourself.

## What ships in `@mercurjs/core`

The core plugin gives you every piece that talks to the provider or writes payout records:

- **Workflows**: `createPayoutAccountWorkflow`, `createOnboardingWorkflow`, `createPayoutWorkflow`, and `processPayoutForWebhookWorkflow`
- **Webhook route**: `POST /hooks/payout` keeps the raw body and emits `payout.webhook_received` with a 5000 ms delay and 3 attempts
- **Webhook subscriber**: `payout-webhook` parses the event through the provider and runs `processPayoutForWebhookWorkflow`
- **Providers**: the built-in `system` provider, plus `@mercurjs/stripe-connector-plugin` as a separate package

## What you wire yourself

No scheduled job, subscriber, or route in core calls `createPayoutWorkflow`. Core also has no `jobs` directory, so nothing captures authorized payments on a timer.

The payout module ships seven scheduled jobs: `payout-sync-onboarding` (every minute), `payout-validate-captures`, `payout-process-transfers` and `payout-process-reversals` (every five minutes), `payout-process-settlements` (daily 01:03 UTC), `payout-alert-failed-operations` (daily 08:04 UTC) and `payout-monitor-kyc` (every six hours, opt-in). Each run is recorded as a `payout_job_run` and can be triggered from `POST /admin/payout-jobs/:job/run`. The events the module emits are `payout_account.updated`, `transfer.failed`, `transfer.reversal_failed`, `payout.failed`, `payout.settlement_created` and `payout.webhook_received`.

The module options configure the pipeline. `resolvePayoutModuleOptions` applies the defaults and every job reads them through `getOptions()`:

| Option | Default | Intended meaning |
| --- | --- | --- |
| `disabled` | `false` | Turn off capture checks and daily payouts |
| `authorizationWindowMs` | `604800000` (7 days) | How long an authorization stays valid |
| `sellerActionWindowMs` | `259200000` (72 hours) | How long a seller has to act on an order |
| `captureSafetyBufferMs` | `86400000` (24 hours) | Margin before authorization expiry |
| `requiredFulfillmentStatus` | `"fulfilled"` | Minimum fulfillment status for a payout |

<Tip>
  Read these options in your own job with `container.resolve(MercurModules.PAYOUT).getOptions()`. That keeps your schedule configurable from `medusa-config.ts`.
</Tip>

## How createPayoutWorkflow computes the amount

`createPayoutWorkflow` takes one `order_id` and pays the seller’s share of that order. It runs 4 stages:

1. Load the order with `total`, `currency_code`, `seller.payout_account`, items, and shipping methods
2. Load every `commission_line` for those items and shipping methods, then sum their `amount`
3. Call `createPayoutStep` with `order.total` minus the commission sum, in the order’s currency
4. Link the payout to the seller and run the `payoutCreated` hook with `order_id` and `payout_id`

For an order with a total of 47.00 and 4.70 in commission lines, the payout amount is 42.30. The workflow throws `Seller does not have a payout account` when the seller has none, and the module throws when the account isn’t `active`.

The provider receives the order id as its idempotency key. With Stripe Connect, the order id also becomes the transfer’s `transfer_group`, and the seller id goes into its metadata.

<Warning>
  `createPayoutWorkflow` doesn’t check payment capture, fulfillment status, or earlier payouts for the order. Each run creates a new `Payout` row. Put those checks in the code that triggers it.
</Warning>

## Trigger payouts from your own code

You decide when an order is ready. This subscriber pays out when Medusa emits `order.fulfillment_created`:

```ts title="src/subscribers/payout-on-fulfillment.ts"
import type { SubscriberArgs, SubscriberConfig } from "@medusajs/framework"
import { createPayoutWorkflow } from "@mercurjs/core/workflows"

export default async function payoutOnFulfillment({
  event,
  container,
}: SubscriberArgs<{ order_id: string }>) {
  await createPayoutWorkflow(container).run({
    input: { order_id: event.data.order_id },
  })
}

export const config: SubscriberConfig = {
  event: "order.fulfillment_created",
}
```

This fires once per fulfillment, so a partially fulfilled order would be paid more than once. Before you ship it, add a guard that skips orders already paid and orders whose payment isn’t captured. A scheduled job in `src/jobs` that scans orders works the same way.

## The provider interface

Every external call goes through `IPayoutProvider` from `@mercurjs/types`. The module loads exactly one provider and throws `Payout module should be initialized with exactly one provider` otherwise.

| Method | Called by | Returns |
| --- | --- | --- |
| `createPayoutAccount` | `createPayoutAccount` | Provider `id`, optional `status`, `data` |
| `createOnboarding` | `createOnboarding` | `data`, such as a Stripe account link |
| `createPayout` | `createPayouts` | Optional `status`, `data` |
| `getWebhookActionAndData` | `getWebhookActionAndData` | A `PayoutWebhookResult` |

When you register no provider, the module loads `system`. It returns `active` accounts and `paid` payouts without moving money, which suits local development and tests. Register Stripe Connect in `medusa-config.ts` with the [Stripe Connect integration](/resources/integrations/stripe-connect).
