A payout account’s status says whether the seller can receive money, and a payout’s status says where one transfer stands. Neither is set by an operator. The provider decides, sends a webhook, and `processPayoutForWebhookWorkflow` writes the new status. Read this page to know when `createPayoutWorkflow` will accept an account, and what each webhook does.

## Account statuses

An account’s state is the `status` field on `PayoutAccount`, typed by the `PayoutAccountStatus` enum from `@mercurjs/types`. It defaults to `pending`, and the provider’s `createPayoutAccount` response can overwrite it.

| Status | Value | Meaning |
| --- | --- | --- |
| `PENDING` | `pending` | Created, setup not finished |
| `ACTIVE` | `active` | Can receive payouts |
| `RESTRICTED` | `restricted` | Missing information or a compliance issue |
| `REJECTED` | `rejected` | Permanently disabled by the provider |

Only `active` matters to the rest of the module. `createPayouts` throws `Account 'pacc_…' is not active` for any other status, so a payout never starts on a pending, restricted, or rejected account.

## Webhooks set the account status

The provider owns the account status, and a webhook carries each change. The provider’s `getWebhookActionAndData` turns a raw webhook into an action and the `pacc` id it applies to. `processPayoutForWebhookWorkflow` then runs the matching step.

The workflow doesn’t check the current status before it writes. Any action can move an account from any status, so the provider’s view always wins:

| Action | Step | New status |
| --- | --- | --- |
| `account.activated` | `activate-payout-account` | `active` |
| `account.restricted` | `restrict-payout-account` | `restricted` |
| `account.rejected` | `reject-payout-account` | `rejected` |
| `not_supported` | none | unchanged |

Each step is `updatePayoutAccountStep`, renamed with `.config({ name })`. It saves the previous status and restores it if the workflow rolls back.

## How Stripe Connect maps account updates

The Stripe Connect provider handles only Stripe’s `account.updated` event, and it reads the `pacc` id from the Stripe account’s `metadata.account_id`. It picks the action in this order:

1. `account.rejected` when `requirements.disabled_reason` starts with `rejected.`
2. `account.activated` when every enabled `accountValidation` check passes
3. `account.restricted` in every other case

The default checks are `detailsSubmitted`, `chargesEnabled`, `payoutsEnabled`, and `noOutstandingRequirements`, all `true`, with no `requiredCapabilities`.

<Note>
  With Stripe Connect, an account can skip `pending` and go to `restricted` first. Stripe sends `account.updated` while the seller is still onboarding, and an account with outstanding requirements maps to `account.restricted`. It becomes `active` on a later update.
</Note>

## Payout statuses

Each payout carries its own `PayoutStatus`. The module creates the row as `pending`, then stores the status the provider’s `createPayout` returns.

| Status | Value | Set by |
| --- | --- | --- |
| `PENDING` | `pending` | Row creation |
| `PROCESSING` | `processing` | A `payout.processing` webhook |
| `PAID` | `paid` | The provider response or a `payout.paid` webhook |
| `FAILED` | `failed` | A `payout.failed` webhook |
| `CANCELED` | `canceled` | A `payout.canceled` webhook |

The Stripe Connect provider returns `paid` as soon as Stripe creates the transfer, and it maps no Stripe event to a `payout.*` action. The `payout.*` branches exist for providers that settle asynchronously.
